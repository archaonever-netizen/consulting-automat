# Промпт для Claude Code — интеграция фреймворка декомпозиции целей

Скопируйте всё ниже в Claude Code. Перед запуском положите в корень репозитория
два файла из предыдущих шагов:
`goal-decomposition-framework.md` (спецификация) и
`claude-system-prompt.md` (системный промпт для движка).

---

```text
РОЛЬ
Ты — старший инженер, выполняющий аккуратную интеграцию в существующую кодовую
базу. Корректность и сохранность инвариантов важнее скорости: ты не срезаешь
углы на верификаторе, безопасности ключа и анти-обман правилах ради того, чтобы
быстрее «получилось». Ты встраиваешься в уже принятые в проекте паттерны, а не
переписываешь их под себя. В неоднозначных местах ты задаёшь вопрос, а не
угадываешь.

КОНТЕКСТ
В корне репозитория лежат два документа:
- goal-decomposition-framework.md — спецификация фреймворка декомпозиции целей
  (модели данных, JSON Schema, логика, анти-обман механизмы, API согласования).
- claude-system-prompt.md — системный промпт для движка Claude и контракт I/O.
Сначала прочитай оба файла целиком — это источник истины. При любом расхождении
между этим брифом и спецификацией приоритет у спецификации; спорные места выноси
мне на решение, не выбирай молча.

ЗАДАЧА
Интегрируй этот фреймворк в существующее приложение: пользователь задаёт одну
измеримую цель, ИИ предлагает декомпозицию месяцы → недели → дни, каждый уровень
согласуется человеком, изменения каскадно пересчитываются и логируются.

ШАГ 0 — РАЗВЕДКА (сделай до написания кода)
1. Обследуй репозиторий: определи фронтенд-фреймворк, бэкенд (если есть), язык,
   менеджер пакетов, систему сборки, БД/хранилище, способ работы с API, наличие
   тестов и CI. Найди, как уже организованы модели, сервисы и состояние.
2. Выведи краткий отчёт: стек, куда логично встроить каждую часть фреймворка,
   какие зависимости добавить, какие риски.
3. Предложи поэтапный план (фазы ниже) и СНАЧАЛА покажи его мне. Не приступай к
   реализации, пока я не подтвержу план. Дальше иди фазами, не всё сразу.

ЖЁСТКИЕ АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ (не нарушать)
- API-ключ Anthropic НИКОГДА не попадает во фронтенд и не коммитится. Все вызовы
  Claude идут через серверную часть (бэкенд-роут или serverless-функция). Если
  бэкенда в проекте нет — НЕ обращайся к API из браузера; остановись и предложи
  мне минимальный серверный слой (или прокси-функцию), затем жди решения.
- Детерминированный ВЕРИФИКАТОР — на сервере, отдельным модулем, и он
  обязателен. Ответ модели показывается человеку ТОЛЬКО после прохождения
  верификатора. Верификатор проверяет как минимум:
    * у каждой метрики валидный source ∈ {user_input, derived, assumption};
    * каждое derived имеет formula + inputs; каждое assumption имеет объект в
      assumptions и needsConfirmationFrom;
    * ни одно user_input не ссылается на данные, которых нет в dataset;
    * закон сохранения: Σ(метрик детей) == метрика родителя (± явный буфер);
    * не нарушены hard-ограничения и зависимости вех;
    * нет confidence="measured" без фактического замера (currentValue+evidence).
  Если проверка падает — НЕ показывай результат; повторно вызови модель,
  приложив список ошибок верификации, максимум N ретраев (сделай N настройкой,
  по умолчанию 2), затем верни управляемую ошибку в UI.
- Движок Claude вызывается строго по контракту из claude-system-prompt.md:
  один уровень за запрос, температура 0, ожидается ровно один JSON-объект.
  Парсинг JSON оборачивай в try/catch; при сбое парсинга — ретрай с указанием
  «верни только валидный JSON».
- НИКОГДА не подменяй отсутствующие данные правдоподобными значениями ни в коде,
  ни в фикстурах, ни в дефолтах. Нехватка данных = dataGap, а не выдуманное число.

ФАЗЫ РЕАЛИЗАЦИИ
Фаза 1 — Слой данных и типы.
  Реализуй модели Goal, Period, Metric, Assumption, DataGap, Constraint,
  ApprovalRecord, ChangeLogEntry по JSON Schema из спецификации. Типы (TS-типы /
  dataclasses / схемы валидации — по стеку) должны делать недопустимые состояния
  непредставимыми, где это возможно (например, source без derivation для derived
  должен быть ошибкой типизации/валидации). Добавь runtime-валидацию по схеме.

Фаза 2 — Верификатор (сервер).
  Чистый, детерминированный модуль verify(parent, children) → Report со списком
  типизированных ошибок (ConservationError, MissingDerivation, FabricatedInput,
  ConstraintViolation, FakeMeasurement, OrphanAssumptionValue). Без обращений к
  сети. Полностью покрыт юнит-тестами, включая негативные кейсы (выдуманное
  число, несходящаяся сумма, ложный measured).

Фаза 3 — Сервис движка (сервер).
  Функция decompose({level, goal, parentNode, dataset, constraints,
  existingAssumptions, request}) → Proposal. Внутри: сборка user-сообщения по
  шаблону из claude-system-prompt.md, вызов Anthropic API, парсинг, прогон через
  верификатор, петля ретраев. Возвращает либо proposed-предложение, либо
  blocked со списком dataGaps. Поддержи request="alternatives".

Фаза 4 — API/состояние и конечный автомат согласования.
  Эндпоинты (или аналог по стеку): создать цель; декомпозировать уровень;
  approve / reject / edit узла; запросить alternatives; confirm/reject
  assumption; recalculate; получить changelog. Реализуй автомат статусов:
  draft → proposed_by_ai → under_review → approved | rejected | needs_revision.
  Спуск на следующий уровень разрешён ТОЛЬКО из approved родителя.
  Каскадный пересчёт при изменении верхнего уровня переводит затронутые
  approved-узлы в needs_revision и СОХРАНЯЕТ ручные правки человека (source=
  user_input), показывая дифф «было → стало», а не затирая молча.

Фаза 5 — UI согласования.
  По рекомендациям UI/UX из спецификации, в стиле существующего приложения:
  вкладки уровней (недели заблокированы до approved месяца, с подсказкой почему);
  цветовая кодировка происхождения метрики (measured / derived с раскрытием
  формулы / assumption пунктиром с именем подтверждающего); панель «Что мне нужно
  от вас» с активными dataGaps и блокировкой кнопки декомпозиции при наличии
  blocksDecomposition; реестр допущений с действиями подтвердить/уточнить/
  отклонить и счётчиком impact; дифф при пересчёте; кнопка «Показать
  альтернативы»; лента аудита с пометкой автора (человек/ИИ). Прогресс выполнения
  опирается только на фактические замеры, не на план.

Фаза 6 — Аудит и наблюдаемость.
  Каждая правка (человека и ИИ) пишется в changeLog: актор (human/ai+версия),
  время, сущность, поле, было/стало, причина, флаг triggeredRecalculation.
  Логируй также факты блокировок верификатором (без утечки секретов в логи).

КАЧЕСТВО И РАБОЧИЙ ПРОЦЕСС
- Пиши тесты вместе с кодом; верификатор и автомат статусов покрой особенно
  плотно. Прогоняй тесты/линтер/типчек перед тем как считать фазу готовой.
- Следуй конвенциям существующего кода (стиль, структура папок, паттерны
  состояния). Не тащи лишние зависимости без согласования.
- Не делай разрушительных операций (массовые правки, миграции, удаление) без
  моего явного подтверждения. Перед каждой фазой — короткий план, после —
  сводка изменений и как проверить.
- Секреты только через переменные окружения; добавь .env.example, обнови
  .gitignore. Ничего секретного в репозиторий.

КРИТЕРИИ ГОТОВНОСТИ (definition of done)
- Можно создать тестовую цель «подразделение в Новосибирске за 6 месяцев», и
  система: при нехватке данных вернёт конкретные dataGaps (без чисел); после
  заполнения предложит разбиение по месяцам с корректными source и сходящейся
  суммой; даст согласовать/отклонить/править; спустится на недели и дни; при
  смене дедлайна каскадно пересчитает с диффом и сохранением ручных правок.
- Верификатор ловит подделанные данные на негативных тестах.
- API-ключ нигде во фронтенде; все вызовы Claude — через сервер.
- Зелёные тесты, типчек и линтер.

Начни с ШАГА 0 и покажи мне отчёт по стеку и план фаз. Жди подтверждения.
```

## Как пользоваться

- Запускайте промпт в корне репозитория, оба `.md`-файла должны лежать рядом.
- Claude Code сначала вернёт отчёт о стеке и план — на этом шаге уточните детали
  (например, если бэкенда нет, выберите вариант прокси-слоя, который он предложит).
- Дальше согласовывайте код по фазам; не давайте проскакивать верификатор и
  правило «ключ только на сервере» — это и есть несущая конструкция защиты от
  выдумывания данных.
```
