# Архитектура ШЕФ — как устроено приложение

Документ написан для владельца продукта: минимум жаргона, максимум сути.
Составлен 12.06.2026 в ходе ревью. Технические детали API — в `README_MIGRATION.md`
и в Swagger (`/docs` на работающем бэкенде).

## 1. Общая картина

```
 Браузер пользователя
 ┌────────────────────────────┐
 │  React-приложение (SPA)    │  16 экранов, один раз загружается,
 │  frontend/                 │  дальше переключает экраны сам
 └─────────────┬──────────────┘
               │ запросы /api/* (JSON, с JWT-токеном)
 ┌─────────────▼──────────────┐
 │  FastAPI-бэкенд (Python)   │  проверяет токен, ходит в БД,
 │  backend/                  │  вызывает ИИ, отдаёт JSON
 └──┬──────────┬──────────────┘
    │          │
 ┌──▼───┐  ┌───▼───────────────┐
 │ БД   │  │ Внешние сервисы:  │
 │SQLite│  │ • Promptra (LLM)  │
 └──────┘  │ • Kaiten (трекер) │
           └───────────────────┘
```

Один и тот же бэкенд раздаёт и само React-приложение (папку `frontend/dist`),
поэтому в проде всё живёт на одном адресе.

**Стек:** Python 3.12 + FastAPI + SQLAlchemy (асинхронно) · React 19 + TypeScript + Vite ·
SQLite · LangChain/LangGraph для ИИ · деплой Docker на Amvera.

## 2. Структура папок

| Папка | Что там |
|---|---|
| `backend/main.py` | точка входа: настройка приложения, список API-разделов, раздача фронтенда |
| `backend/models.py` | описание всех 22 таблиц БД |

| `backend/services/goal_decomposition/` | движок декомпозиции целей + верификатор + свои тесты |
| `backend/core/` | конфигурация (env-переменные), подключение БД, шифрование (Fernet) |

| `frontend/src/services/api.ts` | единая точка запросов к API (axios + подстановка JWT-токена) |

## 3. Экраны и навигация

После входа пользователь попадает в каркас с сайдбаром (`Layout.tsx`). Пункты меню:

| Пункт | Адрес | Экран | Что делает |
|---|---|---|---|
| Главная | `/` | HomePage | приветствие, сводка по клиентам |
| ИИ-Чат | `/chat` | ChatPage | чат с ИИ, история сессий, стриминг ответов |
| Клиенты | `/clients` | ClientsPage → ClientDetailPage → BriefFormPage | список клиентов (аватар, кольцо здоровья) → карточка клиента → заполнение брифа по секциям |
| Цели | `/goals` | GoalsPage → GoalDecompositionPage | список целей → ИИ-декомпозиция цели (месяцы→недели→дни) с проверкой верификатором |
| Сеть агентов | `/orchestration` | OrchestrationPage | запуск мультиагентного анализа по функциям компании, живой прогресс |
| Задачи | `/tasks` | TasksPage | список задач + панель деталей |
| Трекер | `/tracker` | TrackerPage | канбан-доска из Kaiten (если подключён коннектор в профиле) |
| Компания | `/company` | CompanyPage → FunctionDetailPage / DepartmentDetailPage | только для основателя: функции, отделы, матрица связей |
| База знаний | `/knowledge` | KnowledgePage | статьи (редактируемые) + источники (BPMM) |
| (аватар внизу) | `/profile` | ProfilePage | профиль, подключение Kaiten |

Вход: `/login` (LoginPage). Без токена любой адрес перекидывает на логин;
при ответе 401 от API токен сбрасывается и тоже происходит выход на логин.

## 4. Как хранятся данные

Всё — в одной базе SQLite (локально `instance/app.db`, в проде файл `/data/app.db`
на постоянном диске Amvera, который переживает перезапуски).

Главные группы таблиц:
- **Пользователи:** users (+флаг основателя), roles. Пароли — только в виде хэша (bcrypt).
- **Клиенты и брифы:** clients (с профилем размера бизнеса), briefs, brief_sections.
- **Компания:** functions, departments и связи между ними (исполнитель/потребитель/поставщик).
- **Задачи:** user_tasks, task_completions.
- **Чат:** сессии и сообщения (история хранится в БД).
- **Цели:** goal, уровни, узлы дерева, метрики, агрегации (JSON-документ декомпозиции).
- **База знаний:** категории, статьи, источники (BPMM), фрагменты, слои, тексты.
- **Интеграции:** kaiten_connections — токен Kaiten хранится зашифрованным
  (ключ шифрования производится из SECRET_KEY).

На старте бэкенд сам создаёт недостающие таблицы и колонки (безопасно повторять),
создаёт/обновляет основателя из переменных FOUNDER_EMAIL/FOUNDER_PASSWORD
и наполняет базу знаний из файлов BPMM, если она пуста.

В браузере (localStorage) хранится только JWT-токен и id пользователя.

## 5. ИИ-слой

- **LLM-доступ** — через сервис Promptra (`backend/services/llm_client.py`):
  модели deepseek/qwen для чата и агентов, anthropic/claude-opus-4.8 — для
  декомпозиции целей. Ключ — в env (`PROMPTRA_API_KEY`), наружу не отдаётся.
- **ИИ-чат** — стриминг ответов по SSE (текст появляется по мере генерации).
- **Сеть агентов** (LangGraph) — у каждой функции компании свой агент; запрос
  маршрутизируется по связям исполнитель→поставщики→потребители; прогресс
  транслируется на экран. Детали: `ARCHITECTURE_AGENTS.md`.
- **Декомпозиция целей** — отдельный движок со строгим JSON-документом,
  верификатором «анти-обман» (проверка консервации сумм по периодам) и ретраями
  с бэкоффом. Спека: `decompsition/goal-decomposition-framework.md`.
- **База знаний** — статьи и фрагменты BPMM подмешиваются в промпты (дайджест).

## 6. Окружение и деплой

- Настройки — через переменные окружения (`.env.local` локально, env-переменные
  в Amvera): DATABASE_URL, SECRET_KEY, PROMPTRA_API_KEY, FOUNDER_EMAIL/PASSWORD,
  FRONTEND_URL (для CORS) и др. Шаблон — `.env.example`. Секреты в git не попадают.
- Прод: Docker-образ (см. `Dockerfile`) = бэкенд + готовый `frontend/dist` + BPMM.
  Один процесс uvicorn на порту 80. Деплой — push в git Amvera.
- **Золотое правило фронтенда:** после изменений в `frontend/src` пересобрать
  `npm run build` с ПУСТЫМ `VITE_API_URL` и закоммитить обновлённый `dist`
  (см. README.md, раздел «Деплой»).
- Celery/Redis (docker-compose.yml) — заготовка для фоновых задач, в прод не
  деплоится и сейчас не используется.
