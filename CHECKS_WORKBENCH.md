# «Проверки» — инструмент объективной проверки гипотез

Инструмент в разделе **Проекты → Программирование → Проверки** (секция `experiments`).
Ведёт гипотезу через этапы проверки и фиксирует **объективный вердикт**: критерий задаётся
заранее (пороги), к нему прикладываются свидетельства (файлы/ссылки/данные/заметки), и только
тогда открывается «подтверждена/опровергнута». Дополняет инструмент «Гипотезы» (реестр/карта/
конвейер): тот про *формулировку и планирование*, «Проверки» — про *исполнение и доказательство*.

> Включается тем же флагом, что и «Гипотезы»: `hypotheses_workbench`
> (см. [projectFeatureFlags.ts](frontend/src/components/projects/projectFeatureFlags.ts)).
> Связано: [PROGRAMMING_INTEGRATION.md](PROGRAMMING_INTEGRATION.md), [HYPOTHESIS_TEST_PLAN.md](HYPOTHESIS_TEST_PLAN.md).

---

## 1. Ключевой принцип — объективность через ворота

Зеркало «ворот» конвейера гипотез. Вердикт нельзя поставить рукой; он **открывается воротами**:

> критерий задан **заранее** (порог подтверждения/опровержения) → приложено ≥1 свидетельство →
> есть измеренное значение для сверки → только тогда доступны «подтверждена/опровергнута».

Иначе доступно лишь «недостаточно данных». Пороги наследуются из дизайна гипотезы
(`confirmFact`/`refuteFact`), измеренное-vs-порог сверяет человек.

## 2. Этапы проверки

`Дизайн → Сбор свидетельств → Оценка → Вердикт → Следствие` — переход между этапами тоже за
воротами (накопительно). Два вида: **«Карточка»** (степпер + таблица свидетельств + вердикт) и
**«Доска»** (канбан по этапам, drag-and-drop с воротами).

## 3. Модель данных — без изменения контракта

Изолированные поля в lossless-снапшоте секции `experiments` (приём как `lifecycle`/`importance`
у гипотез); `config.fields` и «замок контракта» не трогаются:

- `stage` — этап проверки (`дизайн|сбор|оценка|вердикт|следствие`);
- `evidence` — JSON-массив свидетельств `{ id, kind, title, stance, measuredValue, storagePath?, url?, mime?, size?, addedAt }`;
- вердикт = существующее поле `result` (`подтверждена|опровергнута|недостаточно данных`).

Файлы-свидетельства: **байты** в приватном бакете Supabase Storage, **метаданные** — в `evidence`.

## 4. Замыкание петли

Фиксация вердикта `подтверждена/опровергнута` переводит связанную гипотезу (поле `hypothesis`,
матч по имени) в `lifecycle = результат` — стыковка с конвейером. `недостаточно данных` не двигает.

## 5. Карта кода

**Frontend** (`frontend/src/components/projects/`):
- `projectCheckEvidence.ts` — типы/логика свидетельств (парс/сериализация, сводка). Чистый, тестируемый.
- `projectCheckStage.ts` — этапы, ворота, ворота вердикта, подсказка вердикта, цвет статуса. Чистый.
- `projectCheckLoopback.ts` — петля «вердикт → гипотеза в результат». Чистая функция + обёртка снапшота.
- `ProjectChecksWorkbench.tsx` — вид «Карточка»: степпер, свидетельства (вкл. загрузку файлов), вердикт.
- `ProjectChecksBoard.tsx` — вид «Доска» (канбан по этапам, зеркало `ProjectHypothesisPipeline`).
- монтаж за флагом в `ProjectCanvas.tsx` (карточка `experiments`).

**Backend** (`backend/`):
- `services/check_evidence.py` — файлы-свидетельства в Supabase Storage (scoping `project-<id>/checks/<check_id>/`).
- `routes/projects.py` — `POST/GET/DELETE /{id}/checks/{check_id}/evidence`.
- переиспользуются `services/storage_client.py` (без изменений).

## 6. Тесты

- Юнит: `projectCheckEvidence`, `projectCheckStage`, `projectCheckLoopback`, `check_evidence` (санитайзер/скоупинг/обёртки).
- Smoke-рендер: `ProjectChecksWorkbench` (карточка, файл-свидетельство), `ProjectChecksBoard` (колонки/раскладка).

## 7. Эксплуатация

- Флаг: прод-бандл собран с `VITE_HYPOTHESES_WORKBENCH=1` (код-дефолт остаётся `off`).
- Файлы требуют `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` / бакет в окружении; без них загрузка
  отдаёт понятный 503, остальной инструмент (ссылки/данные/заметки/вердикт) работает.
- Деплой: пересобрать `frontend/dist` перед push (Docker копирует prebuilt dist) — см. памятку Amvera.
