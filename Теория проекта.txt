Экран «Теория проекта» должен не собирать “красивое описание проекта”, а фиксировать проверяемую модель: для кого проект создает ценность, какой результат должен возникнуть, за счет каких компетенций, в каких границах и что нельзя повредить. Это соответствует логике Друкера: теория бизнеса отвечает на вопросы о миссии, компетенциях, клиентах/неклиентах, результатах и должна проверяться на соответствие реальности.

Экран: Теория проекта
0. Верхняя панель экрана

Название: Теория проекта
Статус заполнения: Черновик / Готово к проверке / Методологически валидно / Требует уточнения

Автопроверки:

Миссия не сведена только к деньгам
Указан внешний выгодоприобретатель
Результат измерим
Есть срок результата
Есть источник проверки
Компетенции связаны с результатом
Ограничения включают не только срок
Есть список того, что нельзя разрушить
1. Миссия проекта
Методологический смысл

Миссия отвечает: какую ценность проект создает и для кого. Она не должна быть финансовым желанием. Деньги могут быть результатом, но не единственным смыслом проекта.

Поля
1.1. Для кого проект создает ценность?

Тип: выпадающий список + текстовое уточнение.

Выпадающий список:

Клиенты компании
Сотрудники компании
Собственник / акционер
Подразделение компании
Партнеры
Общество / сообщество
Другое

Если выбрано “Другое” — обязательное текстовое поле.

1.2. Какую проблему или потребность этот проект должен решить?

Тип: текстовое поле.

Вопрос:

Какая конкретная проблема / потребность выгодоприобретателя будет решена проектом?

Валидация:

Ответ должен содержать проблему, а не действие.

Невалидно:

Создать отдел.

Валидно:

Снизить перегрузку центральной команды и ускорить обработку заявок клиентов ЮФО.
1.3. Какое полезное изменение должно произойти?

Тип: текстовое поле.

Вопрос:

Что изменится в работе, состоянии или результате выгодоприобретателя после проекта?

Валидация:

Ответ должен описывать изменение состояния, а не список работ.
1.4. Формулировка миссии

Тип: автособираемое поле + возможность ручного редактирования.

Шаблон:

Проект существует для того, чтобы [выгодоприобретатель] получил [ценность / улучшение],
за счет [изменение в системе],
что позволит [измеримый или наблюдаемый бизнес-эффект].
2. Клиент / выгодоприобретатель
Методологический смысл

Нужно разделить роли: кто платит, кто использует результат, кто получает экономический эффект, на кого влияет проект.

Поля-таблица
Поле	Тип	Вопрос
Заказчик	текст / выбор из ролей	Кто утверждает проект и принимает ключевые решения?
Пользователь результата	текст	Кто будет ежедневно пользоваться созданной системой / процессом / результатом?
Экономический выгодоприобретатель	текст	У кого должен улучшиться финансовый или операционный результат?
Конечный клиент	текст	На какого клиента или внешнюю группу повлияет проект?
Пострадавшая сторона при провале	текст	Кто понесет потери, если проект не будет реализован?
Валидация
Нельзя указать только одного человека без роли.
Должно быть минимум 3 роли: заказчик, пользователь результата, выгодоприобретатель.

Невалидно:

Директор.

Валидно:

Заказчик: директор головной компании.
Пользователь результата: руководитель операционного отдела.
Экономический выгодоприобретатель: головная компания.
Конечный клиент: клиенты ЮФО.
3. Что считаем результатом
Методологический смысл

Результат должен быть измеримым, проверяемым и ограниченным сроком. В OKR-логике key result должен быть measurable; в конце должно быть понятно без спора: выполнено или нет.

Поля-таблица “Критерии результата”

Каждая строка — отдельный критерий.

Поле	Тип	Обязательность
Название результата	текст	обязательно
Тип результата	выпадающий список	обязательно
Метрика	текст	обязательно
Текущее значение	число / текст	желательно
Целевое значение	число / текст	обязательно
Единица измерения	выпадающий список / текст	обязательно
Срок достижения	дата	обязательно
Источник проверки	выпадающий список / текст	обязательно
Кто принимает результат	текст / роль	обязательно

Тип результата:

Финансовый
Клиентский
Операционный
Процессный
Командный
Инфраструктурный
Качественный
Рисковый

Источник проверки:

CRM
Финансовый отчет
Акт приемки
Дашборд
Опрос клиентов
Отчет руководителя
Аудит процесса
Другое
Валидация
Минимум 3 критерия результата.
У каждого критерия есть срок, целевое значение и источник проверки.
Нельзя использовать формулировки “улучшить”, “наладить”, “сделать качественно” без метрики.
4. Ключевые компетенции
Методологический смысл

Компетенция — это способность, без которой проект не может дать результат. У Друкера компетенции должны быть связаны с тем, что организация реально умеет и что ей следует делать; также они должны соответствовать миссии, клиентам и результатам.

Поля-таблица
Поле	Тип
Компетенция	текст
Зачем нужна	текст
С каким результатом связана	выбор из критериев результата
Носитель компетенции	роль / человек / команда
Минимальный достаточный уровень	текст / число
Как проверяем наличие	выпадающий список + описание
Что делаем, если компетенции нет	выпадающий список

Как проверяем:

Интервью
Тестовое задание
Портфолио / кейсы
Прошлый результат
Метрика производительности
Пилотная задача
Аттестация
Другое

Что делаем, если компетенции нет:

Нанять
Обучить
Привлечь подрядчика
Изменить scope проекта
Перенести срок
Отказаться от решения
Валидация
Каждая компетенция должна быть связана минимум с одним критерием результата.
Нельзя указать абстрактную компетенцию без носителя и способа проверки.

Невалидно:

Умение продавать.

Валидно:

Компетенция: продажа B2B-услуг в сегменте малого бизнеса.
Носитель: менеджер продаж.
Проверка: тестовый звонок + конверсия из лида во встречу не ниже 20%.
Связанный результат: 50 новых квалифицированных лидов в месяц.
5. Ограничения
Методологический смысл

Ограничения задают границы, внутри которых результат должен быть достигнут. Это не только срок.

Поле	Тип

5.5. Запреты

Тип: список запретов.

Вопрос:

Что запрещено делать ради достижения результата?

Пример:

Нельзя снижать качество обслуживания клиентов ради снижения затрат.
Нельзя менять CRM на первом этапе.
Нельзя останавливать текущий операционный процесс.
Валидация
Обязательно заполнить срок, бюджет или ресурсный лимит, качество и минимум один запрет.
Если указаны только сроки — блок считается неполным.
6. Что нельзя разрушить
Методологический смысл

Это ядро, которое должно сохраниться при изменениях. Collins/Porras разделяют неизменное ядро — ценности и предназначение — и изменяемые практики, процессы и стратегии.

Валидация
Нельзя указать субъективное состояние без индикатора.
Каждый пункт должен иметь наблюдаемый или измеримый индикатор.

Невалидно:

Валидно:

Что сохраняем: доверие ключевых клиентов.
Индикатор: отсутствие роста жалоб более чем на 10%.
Контроль: еженедельный отчет по жалобам и эскалациям.
Запрещено: переводить ключевых клиентов на новый процесс без пилота.
7. Методологическая проверка экрана

Внизу экрана нужна панель “Проверка теории проекта”.

Проверки
1. Есть внешний или внутренний выгодоприобретатель.
2. Миссия описывает ценность, а не только деньги.
3. Результат содержит измеримые критерии.
4. У каждого результата есть срок и источник проверки.
5. Компетенции связаны с результатами.
6. Ограничения включают срок, ресурс / бюджет, качество и запреты.
7. Список “нельзя разрушить” содержит индикаторы контроля.
8. Нет противоречий между миссией, результатом, компетенциями и ограничениями.

Статусы проверки:

Не заполнено
Заполнено частично
Есть методологические ошибки
Готово к следующему экрану
Итоговая структура экрана
Теория проекта

1. Миссия проекта
2. Клиент / выгодоприобретатель
3. Критерии результата
4. Ключевые компетенции
5. Ограничения
6. Что нельзя разрушить
7. Методологическая проверка

Смысл экрана: не дать пользователю написать произвольный текст. Он должен собрать проверяемую теорию проекта: ценность, выгодоприобретатель, измеримый результат, необходимые способности, границы выполнения и сохраняемое ядро. Если хотя бы один блок нельзя проверить фактами, цифрами, ролью или источником данных — экран не должен считаться заполненным.
