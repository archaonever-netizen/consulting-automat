# Связи и архитектура раздела «Теория проекта» (экран «Весь проект»)

Документ описывает, как устроен слой визуализации Теории проекта на экране **«Весь проект»**:
из чего собираются узлы, какие бывают связи, откуда они берутся (реальные данные vs каркас),
как это рендерится и как это расширять на следующие разделы.

> Кратко: **связи бывают двух родов.** Каркас (раздел → Миссия → блоки → элементы) задаётся экраном.
> Смысловые связи (пунктир с подписями) берутся из **реальных полей-ссылок Теории**, которые
> пользователь заполняет в редакторе; на графе ничего «вручную» не дорисовывается.

## 2. Поток данных

```
Редактор Теории (ProjectTheoryCanvas)
  └─ хранит форму TheoryForm в снапшоте (localStorage)   ← ссылки хранятся как ID
        │  projectTheorySnapshot.read/write
        ▼
buildProjectEditModel(projectId)  →  buildTheoryEditable()
  └─ EditableCard: fields (скаляры Миссии) + lists (6 блоков, items{id,label,values})
        │  ID ссылок здесь превращаются в ТЕКУЩИЕ метки (refLabel) — только для показа
        ▼
buildTheoryGraph(projectId, expanded)        ← projectTheoryGraph.ts
  └─ узлы + рёбра (резолв ссылок по совпадению метки)
        ▼
ProjectDependencyGraph (React Flow)          ← раскладка + кастомные рёбра + интерактив
```

**Источник истины** — `TheoryForm` в снапшоте: `mission` (скаляры) + 6 массивов
(`stakeholders`, `criteria`, `competencies`, `constraints`, `qualityIndicators`, `preserveElements`)
+ счётчики `next*Id`. Поля-ссылки хранят **ID** элемента, а не текст (см. §6).

## 3. Узлы графа

`buildTheoryGraph` возвращает `{ nodes, edges }`. Виды узлов:

| Тип узла | id | Что это |
|---|---|---|
| `sectionNode` | `section:project-theory` | **Верхний «слой разделов»**: карточка-ссылка на раздел. Сейчас один — «Теория проекта». Позже сюда добавятся остальные экраны. |
| `missionNode` | `mission` | **Корень раздела** — Миссия проекта (формулировка из `finalStatement`). |
| `blockNode` | `block:<list>` | Один из 6 блоков Теории. |
| `itemNode` | `item:project-theory:<list>:<id>` | Элемент блока (показывается при раскрытии блока). |

6 блоков (`THEORY_BLOCKS`) строго в порядке экрана:

| `list` | Заголовок | поле имени (`nameField`) |
|---|---|---|
| `stakeholder` | Клиент / выгодоприобретатель | `details` |
| `results` | Критерии результата | `statement` |
| `competencies` | Ключевые компетенции | `name` |
| `constraints` | Ограничения | `statement` |
| `quality` | Качество | `requirement` |
| `preserve` | Что нельзя разрушить | `details` |

## 4. Рёбра графа

Четыре вида (`TheoryEdgeKind`): два «реальных смысловых» (`ref`) и три каркасных.

### 4.1. Каркас (задаётся экраном, виден всегда)

| Вид | Откуда → куда | Смысл |
|---|---|---|
| `section` | `section:project-theory` → `mission` | «из раздела выходит Миссия» |
| `origin` | `mission` → каждый из 6 `block:*` | «из Миссии вытекают блоки Теории» |
| `containment` | `block:*` → его `item:*` | вложенность элементов в блок (при раскрытии) |

Каркас **не зависит от данных**: он одинаков у пустого и заполненного проекта.

### 4.2. Смысловые связи (`ref`) — из реальных полей Теории

Резолвятся по совпадению метки и показываются по наведению/фиксации. Два реестра в
[`projectTheoryGraph.ts`](frontend/src/components/projects/projectTheoryGraph.ts):

**Визуальная грамматика связей** (масштабируется на все разделы), реестр в
[`projectTheoryGraph.ts`](frontend/src/components/projects/projectTheoryGraph.ts):
- **Цвет линии = семейство сущности-цели** (`ENTITY_COLORS`/`entityColor`): стейкхолдер — синий,
  результат — циан, компетенция — фиолет, ограничение — красный, качество — янтарь, сохраняемое — розовый.
- **Тип линии (пунктир + толщина) = род связи** (`EDGE_FAMILIES`): каркас (сплошная толстая),
  декомпозиция Миссия→блоки (сплошная), вложенность блок→элементы (сплошная тонкая),
  смысловая `ref` (пунктир).
- **Точную семантику несёт подпись** на связи («требует», «обеспечивает»…), поэтому отдельный
  цвет на каждый глагол не нужен — палитра остаётся читаемой при росте числа типов связей.

Граф берёт визуал из `edgeVisual(kind, targetId)`, легенда на экране — из тех же `EDGE_FAMILIES`
+ `ENTITY_COLORS` + `THEORY_REF_LEGEND`. **При добавлении раздела новые цвета/типы линий не нужны** —
только подписи связей (их вид выводится из грамматики).

**`MISSION_LINKS`** — точные ссылки Миссии на элементы (поле Миссии → блок):

| Поле Миссии | → блок | подпись |
|---|---|---|
| `mainBeneficiary` | stakeholder | выгодоприобретатель |
| `relatedResults` | results | результат |
| `relatedCompetencies` | competencies | компетенция |
| `protectRelations` | preserve и constraints | нельзя нарушить |

**`BLOCK_LINKS`** — связи элемент → элемент (поле элемента-источника → блок-цель):

| Источник.поле | → блок | подпись |
|---|---|---|
| `stakeholder.resultCriterion` | results | отвечает за |
| `results.requiredCompetencies` | competencies | требует |
| `competencies.resultCriterion` | results | обеспечивает |
| `constraints.resultCriterion` | results | ограничивает |
| `quality.resultCriterion` | results | контролирует |
| `quality.beneficiary` | stakeholder | для |
| `preserve.stakeholder` | stakeholder | защищает |
| `preserve.resultCriterion` | results | сохраняет |
| `preserve.constraint` | constraints | связано с |

### 4.3. Как резолвится `ref`

1. В `EditableCard` значение ссылочного поля — это **метка** целевого элемента (ID уже
   преобразован в текущее имя через `refLabel`).
2. `buildTheoryGraph` строит индекс «метка → id элемента» для каждого блока.
3. Значение поля токенизируется (`,`/`;`) и матчится по метке против индекса блока-цели.
4. Ребро создаётся **только между присутствующими** (раскрытыми) элементами.

> Следствия: чтобы связь появилась, у элемента должно быть **название** и нужно **выбрать**
> его в соответствующем поле-ссылке. На пустом проекте `ref`-рёбер нет вообще (есть тест).
> Риск: два элемента с одинаковым названием → возможна неоднозначность (резолв по метке).
> Более «железобетонно» — резолвить по сохранённому ID (потенциальное улучшение).

## 5. Рендер и интерактив ([`ProjectDependencyGraph.tsx`](frontend/src/components/projects/ProjectDependencyGraph.tsx))

**Раскладка — вертикальное дерево** (функция `layout`):
- `sectionNode` сверху, под ним `missionNode`, ниже — столбец из 6 блоков.
- Элементы раскрытого блока встают **столбиком справа** от него (родитель→дети слева-направо).
- **Динамические ярусы**: высота яруса = `max(высота блока, высота стопки элементов)`,
  поэтому раскрытый блок раздвигает соседей по вертикали — элементы не наезжают на чужие блоки.

**Кастомные рёбра** (на `BaseEdge`):
- `TreeEdge` — ортогональные пути со скруглением для каркаса: `origin` идёт слева единым
  «стволом» (рейка `TRUNK_X`), `containment` — рейкой справа от блока (`CHILD_RAIL_X`),
  `section` — прямой вертикалью по оси столбца.
- `BusEdge` — смысловые `ref`: вертикальный участок выносится на отдельную **дорожку** `laneX`
  справа; `jog` разносит старты связей с общим источником; `labelT` ставит подпись на своей
  высоте — чтобы линии и подписи разных связей не накладывались. Цвет/пунктир/толщина — из
  `edgeVisual(kind, targetId)` (визуальная грамматика, см. §4.2).

**Интерактив:**
- Наведение на узел — временная подсветка его связей.
- **Клик по узлу — фиксирует** связи (pin, рамка `is-pinned`); повторный клик снимает.
- **Двойной клик по узлу — открывает раздел** Теории (`onOpenCard('project-theory')`).
- Наведение на связь — подсветка (`is-hot`); **клик по связи — фиксирует** её отдельно.
- Клик по пустому полю — снимает все закрепления.
- Видимость `ref`: узел активен (закреплён/наведён) **или** сама связь зафиксирована/наведена.
  Дорожки/высоты подписей назначаются плотно **только среди видимых** связей.

## 6. Где хранятся ссылки и кто их резолвит

- **Ручной ввод в редакторе Теории** хранит ссылки как **ID** (выпадашки пишут `option.value`).
  `refLabel(options, id)` превращает ID → актуальную метку только для показа. Поэтому связь
  переживает переименование и не путается при дублях — внутри Теории всё по ID.
- **ИИ-Методолог** (`applyTheoryEdit`) присылает текст, но перед записью **резолвит его в ID
  существующего элемента**: id → точная метка → **однозначное** частичное совпадение.
  Если элемент не найден — **сырой текст не пишется**, а в ответ идёт просьба
  «Сначала добавьте элемент …». Эта гарда — **только в Теории** (другие разделы пишут текст
  без проверки; см. их аппликаторы в `projectEditApplier.ts`).

## 7. Как добавить следующий раздел в этот слой

Слой `sectionNode` спроектирован под расширение: сейчас одна карточка-раздел, дальше — все экраны.
Рекомендуемый порядок при подключении нового раздела (по образцу Теории):

1. **Определи блоки раздела** (его списки и порядок) — аналог `THEORY_BLOCKS`.
2. **Опиши реестры связей** для раздела:
   - каркасные (`origin`-подобные: корень раздела → блоки);
   - смысловые (`ref`): поле-источник → блок-цель, по **реальным** полям-ссылкам раздела.
   Не выдумывай связи — бери только структурные поля-ссылки (как `MISSION_LINKS`/`BLOCK_LINKS`).
3. **Сделай билдер графа** раздела (аналог `buildTheoryGraph`), возвращающий `{ nodes, edges }`
   из `buildProjectEditModel`. Резолв `ref` — по существующим элементам (метка, а лучше ID).
4. **Переиспользуй рендер**: те же `TreeEdge`/`BusEdge` и принципы раскладки (корень → блоки →
   элементы справа, дорожки для `ref`). При обобщении вынеси раскладку/рёбра в общий модуль.
5. **Подключи раздел к слою**: добавь его `sectionNode` рядом с «Теорией проекта» и связь
   `section → корень раздела`. Межсекционные связи (раздел↔раздел) описывай отдельным реестром
   и резолвь по реальным `*Ref`-полям (часть уже есть в
   [`projectCrossRefs.ts`](frontend/src/components/projects/projectCrossRefs.ts)).
6. **Гарда ссылок в аппликаторе** раздела (как в Теории): нет id → не писать текст, просить
   добавить элемент. Сейчас это реализовано только для Теории — при расширении вынеси в общий хелпер.

**Главный инвариант:** на графе визуализируются только реально предусмотренные в проекте
зависимости (из полей-ссылок), плюс методологический каркас. Любую новую связь сначала заводи
как поле-ссылку в данных раздела, потом — в реестр графа.

## 8. Что НЕ визуализируется (намеренно)

- «Мягкие» зависимости, заданные не структурной ссылкой, а словарной опцией (например
  `result.beneficiary` — общий список вариантов, `competency.strategicChoice` — ссылка на другой
  раздел статической опцией). Граф их не выдумывает.
- Межсекционные связи: экран «Весь проект» сейчас **только про Теорию**; реестр `projectGraphModel.ts`
  (фазовый каркас + кластеры для всех разделов) сохранён как основа на будущее, но к экрану не подключён.
