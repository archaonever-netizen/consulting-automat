# Композиция раздела проекта (Section Composition)

Документация инструмента «Композиция раздела» в модуле **Проекты**. Описывает, что это,
как устроено, какие приняты архитектурные решения, где лежит код, как расширять и какие есть
известные подводные камни. Цель файла — чтобы не объяснять всё заново каждый раз.

> Связанные документы: [THEORY_GRAPH.md](THEORY_GRAPH.md). Память сессий: `memory/section-composition.md`.

---

## 1. Что это и зачем

«Композиция раздела» — это **read-only пересказ** одного экрана проекта человеческим языком:
ИИ берёт данные, которые сотрудник внёс в рабочую форму раздела, и собирает из них связный
структурированный документ (манифест + текст по блокам). Это НЕ редактор и НЕ генератор новых
данных — только пересказ уже введённого.

Результат показывается в правой панели воркспейса проекта и переиспользуется клиентским
порталом (нарратив «Проект»).

### Две кнопки = два режима

В `ProjectToolbar` две кнопки, обе вызывают `runComposition(mode)` в
[ProjectWorkspace.tsx](frontend/src/components/projects/ProjectWorkspace.tsx):

| Кнопка | mode | Что делает | Стоимость |
|---|---|---|---|
| **Композиция раздела** | `'full'` | Пересобирает ВСЕ блоки (deepseek→sonnet), затем один проход сильной модели на весь раздел: review (Opus) → finalize (sonnet) | Дорого |
| **Обновить изменённое** | `'incremental'` | Пересобирает только блоки, чьи данные изменились (кэш по хешу). Без Opus, без finalize | Дёшево / часто бесплатно |

Инкрементальный режим сравнивает хеш исходного текста каждого блока с сохранённым: совпал —
берётся готовый текст из кэша **без вызова модели** (`status='cached'`), иначе пересобирается
только этот блок. Поэтому точечная правка проекта меняет лишь один блок, остальной текст —
байт-в-байт прежний.

## 2. Поток данных (сверху вниз)

```
[Рабочая форма раздела] (редактор-канвас, snapshot в localStorage + БД)
        │
        ▼
[Источник-текст экрана]  ── frontend собирает строку с блоками «### Заголовок»
        │                   (см. §3 — два пути: «леса» и прежний)
        ▼
[splitIntoBlocks]        ── режет текст на блоки по «###», id блока = заголовок
        │
        ▼
POST /api/projects/{id}/composition/stream   (SSE)
   body: { project_model: {project, section, blocks}, card_id, mode }
        │
        ▼
[compose_stream]  backend/services/project_methodolog.py
   • по каждому блоку: deepseek → sonnet (или кэш)
   • _assemble_blocks → манифест
   • mode='full': review (Opus) → finalize (sonnet)
   • чекпоинт в БД на каждом этапе
        │
        ▼  SSE-события: type='block' (running/done/cached/fallback),
        │              type='stage' (review/finalize), финал type='done'
        ▼
[onDone] frontend сохраняет манифест+текст, рендерит CompositionBody
```

## 3. Источник данных — ключевое решение

Источник — это **текстовая строка с блоками вида `### Заголовок` + содержимое**, которую фронт
формирует ДО отправки. На бэкенд уходит уже нарезанный список блоков. Есть **два пути**, и выбор
сделан в `runComposition`:

### 3.1 Путь «строительные леса» (Вариант 1) — для сложных карточек

Применяется к **`diagnosis`, `strategic-choice`, `target-state`, `strategy-map`**.
Файл: [projectCompositionSource.ts](frontend/src/components/projects/projectCompositionSource.ts),
функция `buildScaffoldedCompositionText`.

Идея «по образцу Теории»: каждый блок раздела **выводится ВСЕГДА** — с заголовком `###` и
**методологическим пояснением** (строительные леса), даже если поля пусты. Под пояснением —
реально внесённые данные рабочей формы.

- Пояснения заданы декларативно в реестре `CARD_SCAFFOLDS` (текст взят из примечаний
  редакторов: `DiagnosisSection`/`StrategicSection`/`TargetSection`).
- Данные берутся из **единой рабочей модели** `buildProjectEditModel`
  ([projectEditModel.ts](frontend/src/components/projects/projectEditModel.ts)) — это та же
  форма, что отображается в левом компактном канвасе. Поэтому композиция видит данные тогда же,
  когда их видно слева.
- Текст **никогда не пуст** → бэкенд не отдаёт «нет данных» (как и Теория).

Каждый блок привязан либо к подмножеству скалярных полей (`kind:'scalars'`, по ключам), либо к
списку (`kind:'list'`, по id списка = `projKey`). Структура берётся из спеки карточки
(`COMPLEX_CARDS` в [projectComplexCards.ts](frontend/src/components/projects/projectComplexCards.ts)
или конфиг секции), в реестре лежат только пояснения — без дублирования структуры.

### 3.2 Прежний путь — для «Теории проекта» и остальных карточек

`buildCardValidationText`
([projectCardValidation.ts](frontend/src/components/projects/projectCardValidation.ts)) — тот же
сериализатор, что использует ИИ-валидатор. Для «Теории» он читает `snap.blocks` (рабочую
проекцию), у которой в каждом блоке есть **встроенные фоллбэк-пояснения**
(`fallbackExpectedState`/`output` в
[projectTheorySnapshot.ts](frontend/src/components/projects/projectTheorySnapshot.ts)) — поэтому
Теория исторически собиралась надёжно и никогда не была пустой.
Если этот источник пуст — фолбэк на компактную form-модель
(`buildCompactSectionModel` → `compactModelToText`).

> **Почему так:** «Теория» — методологически особая карточка (singleton-миссия + 6 списков с
> кросс-ссылками) и настраивалась первой. Сложные карточки имели другую архитектуру (только
> подписи полей, без пояснений в данных) и читали хрупкую верхнеуровневую проекцию, которая
> пустела без открытого редактора. «Леса» (§3.1) приводят их к поведению Теории, не трогая
> прежний путь и не дублируя работу на каждой карточке.

## 4. Конвейер моделей

Модели в формате Promptra `provider/model`, константы в
[project_methodolog.py](backend/services/project_methodolog.py):

| Этап | Константа | Модель | Что делает |
|---|---|---|---|
| 1. collect (на блок) | `COMPOSE_COLLECT_MODEL` | `deepseek/deepseek-v4-pro` | Пересказ данных блока |
| 2. structure (на блок) | `COMPOSE_STRUCTURE_MODEL` | `anthropic/claude-sonnet-4.6` | Читаемый markdown блока |
| 3. review (на весь раздел, только `full`) | `COMPOSE_REVIEW_MODEL` | `anthropic/claude-opus-4.8` | Ёмкие правки по изложению |
| 4. finalize (только `full`, и только если review='revise') | `COMPOSE_FINALIZE_MODEL` | `anthropic/claude-sonnet-4.6` | Внести правки рецензента |

- Сборка блока: `_run_block` (collect → structure). Заголовок блока добавляется детерминированно
  при сборке (`_assemble_blocks`), модель его не пишет.
- Манифест: `_run_manifest` (sonnet), регенерится только если что-то менялось.
- Все вызовы идут через `_chat_json`
  ([methodolog.py](backend/services/methodolog.py)) — OpenAI-совместимый клиент Promptra со
  стримингом и спасением оборванного JSON (`strict=False`, `_salvage_json`).

> **Важно (частый вопрос):** этот конвейер **НЕ использует «Сеть агентов» (`agent_network`)**.
> Это отдельный, более дешёвый пайплайн: дорогой Opus видит уже сжатый текст, а не весь
> PROJECT_MODEL. Композиция всегда идёт **по одному разделу за раз**.

## 5. Долговечность (чекпоинт + гидрация)

Композиция переживает обновление страницы и рестарт сервера.

- Чекпоинт хранится в `ProjectCardState` в синтетической строке `__composition__:<card_id>`.
  Хелперы: `get_composition` / `save_composition_stage` / `reset_composition`
  ([project_cards.py](backend/services/project_cards.py)).
- `save_composition_stage` коммитит **на каждом этапе** — это защита от падения: завершённые
  блоки уже в БД, обрыв SSE теряет максимум один незавершённый этап.
- В чекпоинте лежат: `block_cache` (хеш+текст по каждому блоку), `order`, `manifest`, `final`.
- Фронт при заходе на карточку тянет чекпоинт `GET /api/projects/{id}/composition`
  (`fetchCompositionState`) и показывает сохранённый `final` через `applyCompositionState`
  **БЕЗ пересчёта**. Эндпоинт сброса: `POST /composition/reset`.

> ⚠️ **Следствие (важно понимать):** на экране может висеть **сохранённый результат прошлого
> запуска**. Если вы добавили данные в карточку, текст композиции сам **не** обновится — нужно
> заново нажать кнопку. «Данные в карточке есть, а пишет, что их нет» — это, как правило, именно
> залипший старый чекпоинт.

---

## 6. Транспорт (SSE)

Единый эндпоинт `POST /api/projects/{id}/composition/stream` (`compose_stream`). Фронт читает
поток через `fetch` + `getReader` (`streamComposition` в
[projectReview.ts](frontend/src/components/projects/projectReview.ts)), как `OrchestrationPage`.
Прогресс рисуется степпером из событий `type='block'` и `type='stage'` в `ProjectWorkspace`.

## 7. Карта кода

**Frontend** (`frontend/src/components/projects/`):
- `ProjectWorkspace.tsx` — `runComposition`, выбор источника, `splitIntoBlocks`,
  `applyCompositionState`, гидрация, рендер степпера и `CompositionBody`.
- `projectCompositionSource.ts` — **«леса»**: реестр `CARD_SCAFFOLDS` + `buildScaffoldedCompositionText`.
- `projectCompositionSource.test.ts` — тест лесов.
- `projectCardValidation.ts` — `buildCardValidationText` (прежний путь, Теория и пр.).
- `projectEditModel.ts` / `projectCompactSectionModel.ts` — единая рабочая модель формы.
- `projectComplexCards.ts` — спеки сложных карточек (`COMPLEX_CARDS`).
- `projectReview.ts` — `streamComposition`, `fetchCompositionState`, `resetComposition`.

**Backend** (`backend/services/`):
- `project_methodolog.py` — `compose_stream`, `_run_block`, `_assemble_blocks`, `_run_manifest`,
  `_run_review`, `_run_finalize`, `_compose_clean`, константы моделей, промпты.
- `project_cards.py` — чекпоинт композиции (`__composition__:<card_id>`).
- `methodolog.py` — `_chat_json`, `_salvage_json`, стриминг.
- `projects.py` — портал-нарратив, читающий сохранённые композиции.

## 8. Как добавить карточку в «леса»

1. Убедиться, что у карточки есть адаптер в `buildProjectEditModel` (для сложных — запись в
   `COMPLEX_CARDS`; для секций — конфиг секции). Это и так нужно для чата-Методолога.
2. Добавить запись в `CARD_SCAFFOLDS` в `projectCompositionSource.ts`: перечислить блоки
   (`scalars(...)` по ключам полей и `list(id, ...)` по `projKey` списка) с заголовками и
   методологическими пояснениями.
3. Готово — структура подтягивается из адаптера, композиция/компакт работают автоматически.
   Бэкенд и транспорт трогать не нужно.

То есть стоимость новой карточки — **декларативная спека**, а не отдельный сериализатор.

## 9. Известные подводные камни и баги

1. **Finalize может затереть готовый текст заглушкой (актуальный баг).**
   В режиме `full`, если этап finalize вернул пустой `composition`, `_compose_clean` подставляет
   строку `"В разделе пока нет данных для композиции."`, а в `compose_stream` строка
   `composition = polished.get("composition") or composition` принимает эту **непустую** заглушку
   и затирает реальную композицию. Внешне: настоящий манифест + заглушка вместо текста, при том
   что деньги за все этапы списаны.
   **Обходной путь без правок:** нажать **«Обновить изменённое»** — инкрементальный режим
   пропускает review/finalize и пересобирает раздел из уже оплаченного блок-кэша (хеши совпадут →
   `cached`), без вызовов модели.
   **Направление фикса:** принимать `polished.composition` только если он непустой и не равен
   заглушке; пустой ответ finalize должен означать «оставить как было».

2. **Залипший чекпоинт.** См. §5 — экран показывает сохранённый результат, пока не пересоберёшь.

3. **Рассинхрон строк пустого раздела.** Конвейер пишет `_SECTION_EMPTY_MSG =
   "В этом разделе пока нет данных для композиции."`, а портал-фильтр в `projects.py` сравнивает
   со старой формулировкой `"В разделе пока нет данных для композиции."` (без «этом») — фильтр
   не срабатывает на реальную заглушку. Историческое: формулировку меняли, фильтр не обновили.

4. **Разбиение по `###`.** id блока = заголовок; дубли заголовков получают суффикс `-2`.
   Заголовки внутри карточки должны быть уникальны (в `CARD_SCAFFOLDS` это соблюдено).

## 10. Почему так (резюме решений)

- **Экономия токенов** — главная цель конвейера: до Opus доходит сжатый текст, а не весь проект;
  инкрементальный режим пересобирает только изменённые блоки.
- **«Леса» вместо правки каждой карточки** — единый form-источник + декларативные пояснения
  приводят все сложные карточки к надёжному поведению Теории без пер-карточного кода.
- **Чекпоинт на каждом этапе** — устойчивость к обрывам SSE и рестартам.
- **Отдельный пайплайн, а не Сеть агентов** — осознанный размен: дешевле и проще для read-only
  пересказа одного экрана.
