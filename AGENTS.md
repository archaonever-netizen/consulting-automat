# Контекст репозитория для ИИ-агентов

Этот репозиторий является локальным lab-клоном основного проекта `consulting-automat`.

Он используется не как основная ветка разработки, а как безопасная рабочая копия для локальных экспериментов, проверки архитектуры и подготовки изменений к переносу в основной репозиторий.

## Назначение репозитория

- Основной репозиторий находится отдельно: `D:\consulting-automat`.
- Этот lab-репозиторий находится здесь: `D:\consulting-automat-lab`.
- В этом репозитории можно разрабатывать и тестировать функционал локально, не затрагивая основную рабочую копию.
- Изменения отсюда должны переноситься в основной репозиторий осознанно, через описание изменений и отдельную проверку.

## Важная логика работы

- Не считать этот репозиторий production-источником истины.
- Не пушить изменения напрямую в основной remote.
- Текущий `origin` настроен для fetch из основного локального репозитория, а push отключен:

```text
origin fetch: D:\consulting-automat
origin push: DISABLED
```

- Для новых задач использовать отдельные ветки.
- Перед переносом в основной репозиторий фиксировать изменения в `docs/TRANSFER_LOG.md`.
- Если изменение временное, экспериментальное или относится только к локальному запуску, явно помечать это в журнале переноса.

## Локальный запуск

Для lab-среды используются отдельные порты:

- Backend: `http://127.0.0.1:8010`
- Frontend: `http://127.0.0.1:5174`
- Локальная база: `instance/local_lab.db`

Основные скрипты:

```powershell
scripts\start-local-lab.ps1
scripts\stop-local-lab.ps1
scripts\create-local-lab-shortcut.ps1
```

Служебные локальные папки:

- `.local-lab/`
- `logs/`
- `.venv/`
- `.pytest_cache/`
- `.ruff_cache/`
- `instance/`

Эти папки обычно не нужно переносить в основной репозиторий как код.

## Как агенту работать с этим репозиторием

1. Сначала проверить текущую ветку:

```powershell
git branch --show-current
```

2. Проверить рабочее дерево:

```powershell
git status --short --branch
```

3. Не удалять и не откатывать чужие изменения без явного запроса пользователя.

4. Перед переносом изменений обновить `docs/TRANSFER_LOG.md`:

- что разрабатывалось;
- что фактически реализовано;
- какие файлы изменены;
- какие тесты запускались;
- какие ошибки найдены и исправлены;
- какие риски и следующие шаги есть.

5. Не добавлять в commit локальные служебные папки:

- `.local-lab/`
- `logs/`
- `.venv/`
- `.pytest_cache/`
- `.ruff_cache/`

6. Если изменялся frontend и в репозитории отслеживается `frontend/dist`, после `npm.cmd run build` нужно учитывать обновленные hash-файлы.

7. Если добавляются новые поля БД, помнить:

- lab-среда может использовать idempotent startup-проверки;
- для основного репозитория предпочтительнее полноценные миграции.

## Перед переносом в основной репозиторий

Перед переносом нужно проверить:

- какие изменения являются общими и нужны в основном проекте;
- какие изменения относятся только к lab-запуску;
- нужен ли перенос `frontend/dist`;
- нужны ли Alembic migrations вместо startup `ALTER TABLE`;
- не попали ли в commit локальные логи, pid-файлы, браузерные профили или секреты.

## Принцип

Этот репозиторий - рабочая лаборатория. Его задача: позволить быстро собрать, проверить и описать изменения так, чтобы затем перенести их в основной проект чисто и без случайного влияния на production-код.
