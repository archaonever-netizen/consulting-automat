# «План проверки» — командное планирование и ведение гипотез

Инструмент в воркспейсе гипотез (раздел **Проекты → Программирование**): команда собирается,
открывает гипотезу, **строит план действий**, **распределяет шаги на сотрудников** и
**выгружает их задачами в Яндекс.Трекер**, чтобы исполнители не потеряли работу из виду.
Статусы тянутся обратно — на следующем сборе видно прогресс.

> **СТАТУС: проектная спека (design spec).** На момент написания функционал **ещё не реализован** —
> документ описывает планируемую архитектуру и план работ, а не существующий код. Пути файлов —
> целевые. По мере реализации помечать разделы готовыми.
>
> Связано: [PROGRAMMING_INTEGRATION.md](PROGRAMMING_INTEGRATION.md) (инструмент гипотез: реестр,
> карта, конвейер, ИИ — на нём строимся), [BPMN_PROCESS_DESIGNER.md](BPMN_PROCESS_DESIGNER.md)
> (почему полноценный BPMN с дорожками — отдельная дорогая веха, в этот объём не входит).

---

## 1. Что это и зачем

Боль: при планировании теста гипотезы **сложно увидеть план действий целиком** и раздать его
людям так, чтобы каждый знал свою часть и не забыл о ней. Гипотеза — крупная задача; её нельзя
«назначить на одного». Нужен интерфейс, где команда вместе видит шаги, роли, последовательность
и контрольные точки, а исполнение уходит туда, где люди работают каждый день.

Объём v1 (выбран заказчиком): **План + схема + Трекер.**

---

## 2. Ключевой принцип (от него зависит вся архитектура)

«Чтобы не потеряли из виду» решается **НЕ внутри приложения, а выгрузкой задач в ежедневный
инструмент исполнителя.** В стратегическое приложение никто не ходит ежедневно; в Трекер — ходят.

Два слоя, разные по аудитории:

| Приложение = комната планирования | Яндекс.Трекер = рабочее место каждого |
|---|---|
| Команда вместе видит **весь план гипотезы**: шаги, кто, порядок, контрольные точки | Сюда **выгружаются задачи по людям** — с уведомлениями и сроками |
| Хранит **смысл**: какой шаг какой вклад вносит в факт | Хранит **исполнение**: статус, комментарии, «мои задачи» |

Назад в приложение тянется **живой статус** — чтобы на сборе видеть, что сделано и что стоит.
Личный список задач внутри приложения НЕ строим — это работа Трекера.

## 3. Интерфейс

Панель **«План проверки»** в детали гипотезы (рядом с группами «Смысл / Как проверим»).

```
ГИПОТЕЗА: «Заводам важна скорость»            🟢 готова к проверке
ЧТО ДОКАЗЫВАЕМ:  ≥3 из 10 заводов согласятся на +15% за доставку 2 дня
──────────────────────────────────────────────────────────────
ПЛАН ПРОВЕРКИ                         [+ шаг]   [Выгрузить в Трекер ⤴]

 1 ▸ Спроектировать опрос и порог
     Кто: Ольга · методолог      Срок: 3 дн     ● в работе  TASK-101
     Вклад: единый список вопросов, единый критерий

 2 ▸ Поднять данные по срокам отгрузки
     Кто: Игорь · аналитик       Срок: 5 дн     ○ открыта   TASK-102
     Вклад: факт — какая скорость сейчас

 3 ▸ 10 интервью с заводами
     Кто: Аня · продакт          Срок: 10 дн    ○ открыта   TASK-103

 ◆ 4 ▸ Свести свидетельства и сравнить с порогом   ← КОНТРОЛЬНАЯ ТОЧКА
     Кто: Ольга                  Зависит от: 1,2,3
     Вклад: один факт — подтверждена / опровергнута / недостаточно
──────────────────────────────────────────────────────────────
Готовность: 1 / 4 шага · ближайший дедлайн: 3 дн · владелец вердикта: Ольга
```

Авто-схема потока из тех же шагов (лёгкая, без bpmn-js — div+CSS, как Карта/Конвейер):

```
[1 Ольга]→[2 Игорь]┐
                    ├→ ◆[4 Ольга: синтез]→ вердикт
        [3 Аня]────┘
```

Элементы и зачем:
- **Шапка «что доказываем»** — держит команду на пороге, а не «просто задачах».
- **Шаги**: что · кто · роль · срок · вклад в факт · зависимость — это «распределить на людей».
- **Контрольные точки (◆)** — где команда пересобирается и допиливает план.
- **Один владелец вердикта** — шаг синтеза всегда на одном человеке.
- **Выгрузить в Трекер** — шаги → задачи исполнителям (механизм «не потеряют»).
- **Живой статус + готовность** — тянется из Трекера, видно на сборе.

## 4. Модель данных (без изменения контракта)

Новое **изолированное поле** `plan` на гипотезе — JSON-строка со списком шагов. Тот же приём,
что `importance`/`uncertainty`/`lifecycle`: лежит в lossless-форме секционного снапшота
(`form` у карточки `hypotheses`), общий `config.fields` и характеризационный «замок контракта»
НЕ трогаем (поле не входит в `config.fields`, существующие тесты не падают).

```ts
interface PlanStep {
  id: string;
  action: string;          // что сделать
  assignee: string;        // кто (см. §7.1 про маппинг в Трекер)
  role: string;            // методолог / аналитик / продакт / …
  contribution: string;    // какой вклад в факт
  dueDate: string;         // срок
  dependsOn: string[];     // id шагов-предшественников
  isCheckpoint: boolean;   // контрольная точка
  trackerKey?: string;     // ключ задачи после выгрузки (QUEUE-123)
  trackerStatus?: string;  // последний подтянутый статус
}
```

Парсинг/сериализация — в компоненте (`JSON.parse/stringify` поля `values.plan`).

## 5. Бэкенд (переиспользуем готовую интеграцию Трекера)

Уже есть в [backend/routes/tracker.py](backend/routes/tracker.py):
- `POST /api/tracker/issues` — создать задачу (`TrackerIssueCreate`: `queue, summary, description, assignee, tags`).
- `POST /api/tracker/issues/search` / `GET /api/tracker/issues/{key}` — статусы.
- `GET /api/tracker/queues`, `GET /api/tracker/connection` — очереди и подключение.
- Клиент: [yandex_tracker_client.py](backend/services/yandex_tracker_client.py) (`create_issue`, `search_issues`, …).

**Предложение:** тонкий эндпойнт-обёртка `POST /api/projects/{id}/hypotheses/plan/push`:
- принимает `{ hypothesisLabel, threshold, steps: PlanStep[], queue }`;
- создаёт по задаче на шаг: `summary = action`, `description = вклад + «что доказываем» + порог + роль/исполнитель`, `tags = ["гипотеза-{id}"]`;
- возвращает `[{ stepId, key }]`.
- Цель — держать формат описания в одном месте и не гонять N запросов с фронта.
- Альтернатива без нового эндпойнта: фронт зовёт `/api/tracker/issues` по разу на шаг.

## 6. Фронтенд (в воркспейсе гипотез, за флагом `hypotheses_workbench`)

- Панель **«План проверки»** в [ProjectHypothesesWorkbench.tsx](frontend/src/components/projects/ProjectHypothesesWorkbench.tsx) (деталь гипотезы): редактируемый список шагов (добавить/удалить, контрольная точка, зависимости).
- Компонент **схемы потока** — новый лёгкий `ProjectHypothesisPlanFlow.tsx` (раскладка по зависимостям, div+CSS), по образцу [ProjectAssumptionMap.tsx](frontend/src/components/projects/ProjectAssumptionMap.tsx) / [ProjectHypothesisPipeline.tsx](frontend/src/components/projects/ProjectHypothesisPipeline.tsx).
- Кнопка **«Выгрузить в Трекер»** → сохраняет `trackerKey` в шаги, переводит гипотезу в `lifecycle = идёт` (стыковка с конвейером).
- Кнопка **«Обновить статусы»** → тянет статусы по ключам, пишет в `trackerStatus` (pull; без вебхуков в v1).
- Запросы — через существующий `api` (axios).

## 7. Открытые решения (подтвердить до старта)

1. **Кто исполнитель в Трекере.** `assignee` Трекера требует логин/uid, а «кто» в шаге — свободный
   текст. **v1 (рекомендовано):** не назначать автоматически — писать человека в описание задачи;
   назначение вручную в Трекере. Пикер пользователей Трекера (нужен новый эндпойнт списка
   пользователей, которого пока нет) — отдельная веха.
2. **Одна задача на шаг vs родитель+подзадачи.** **v1:** плоские задачи с тегом `гипотеза-{id}`;
   эпик/подзадачи — позже.
3. **Очередь.** Брать `default_queue` из подключения или выбирать из `GET /queues` при выгрузке.
4. **Подключение Трекера — на пользователя** (OAuth). Выгружает тот, кто ведёт сессию. Для v1 ок.
5. **Статусы — ручное обновление** (кнопка) в v1; авто-синхрон/вебхуки — позже.

## 8. Стыковка и безопасность

- **Жизненный цикл:** выгрузка плана → гипотеза в «Идёт проверка»; закрытие контрольного шага
  синтеза → запрос результата → «Результат» (далее Решение/Урок).
- **Безопасность:** всё за флагом `hypotheses_workbench`, на общих данных, поле `plan` изолированное —
  старый раздел и контракт не затрагиваются. Бандл (`frontend/dist`) пересобрать перед деплоем
  ([amvera-deploy] gotcha).

## 9. План работ (поэтапно, каждый этап — отдельный коммит, под тестами)

### Этап A — Модель и список шагов (приложение, без Трекера)
- [ ] Чистый модуль `projectHypothesisPlan.ts`: типы `PlanStep`, парсинг/сериализация `plan`,
      хелперы (готовность, ближайший дедлайн, валидация зависимостей). + юнит-тесты.
- [ ] Панель «План проверки» в детали гипотезы: список шагов с полями, добавление/удаление,
      контрольная точка, зависимости. Сохранение в `values.plan` тем же путём. + smoke-тест.

### Этап B — Авто-схема потока
- [ ] `ProjectHypothesisPlanFlow.tsx`: раскладка шагов по зависимостям, контрольные точки
      выделены, исполнитель на коробке (div+CSS, без bpmn-js). + smoke-тест.
- [ ] Переключатель «список ↔ схема» внутри панели плана.

### Этап C — Выгрузка в Трекер
- [ ] Бэкенд: `POST /api/projects/{id}/hypotheses/plan/push` (формат описания, тег, создание задач)
      + санитайзер + тест; регистрация роута.
- [ ] Фронт: кнопка «Выгрузить в Трекер» (выбор очереди), сохранение `trackerKey`, перевод
      гипотезы в `lifecycle = идёт`. Обработка «Трекер не подключён» (409) — понятная подсказка.

### Этап D — Возврат статусов
- [ ] Кнопка «Обновить статусы»: запрос статусов по ключам, запись `trackerStatus`, отображение
      на шагах и в схеме.

### Этап E — Замыкание петли с результатом
- [ ] Когда контрольный шаг синтеза закрыт в Трекере → подсказка занести результат гипотезы
      (подтверждена/опровергнута/недостаточно) → перевод в «Результат».

### Этап F — Сборка и деплой
- [ ] Прогон тестов (фронт+бэк), `tsc --noEmit`, пересборка `frontend/dist`, коммит, push в Amvera.

## 10. Тесты

- **Юнит:** парсинг/сериализация `plan`, готовность/дедлайн/валидация зависимостей; санитайзер
  выгрузки на бэке.
- **Smoke-рендер:** панель плана и схема потока монтируются и показывают шаги/исполнителей.
- **Чек «ничего не сломалось»:** старый раздел при выключенном флаге; существующие тесты «Проекты»
  и Трекера зелёные; типы чистые.
